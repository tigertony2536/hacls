# HACLS Project Charter

## วิสัยทัศน์

HACLS เป็นคลังความรู้ร่วมที่เชื่อมการเรียนรู้ของเจ้าของโครงการกับการพัฒนาแบบ Agentic ให้ความรู้ที่เรียนรู้แล้วนำไปใช้กับ Agent ได้ และทำให้สิ่งที่ Agent เรียนรู้จากการทำงานกลับมาเป็นความรู้ที่ตรวจสอบและนำไปใช้ซ้ำได้

Repository นี้เป็นแหล่งอ้างอิงหลัก (source of truth) สำหรับเจ้าของโครงการและ Agent จากโปรเจกต์อื่น Agent จะดึงความรู้ที่เกี่ยวข้องไปใช้ โดยไม่ถือว่าข้อเสนอที่ยังไม่ผ่านการตรวจเป็นแนวทางปฏิบัติ

## ปัญหาที่ต้องการแก้

- การเรียนรู้ของเจ้าของโครงการไม่เชื่อมกับการนำความรู้นั้นไปใช้ใน Agentic development
- ความรู้ที่ได้จาก Agent กระจัดกระจายและยากต่อการค้นหา ตรวจสอบ และนำกลับมาใช้
- Agent ขาดแหล่งอ้างอิงร่วมที่ชัดเจนสำหรับการสร้างและปรับปรุง skills

## ผู้ใช้และบทบาท

- **เจ้าของโครงการ:** เรียนรู้ จัดระเบียบ ตรวจสอบ และตัดสินว่าความรู้ใดควรเป็นแหล่งอ้างอิงหลัก
- **Agent:** อ่านความรู้ที่เกี่ยวข้อง นำไปใช้ในงาน เสนอสิ่งที่เรียนรู้หรือการแก้ไขพร้อมหลักฐาน และสร้าง skills ที่อ้างอิงความรู้ต้นทาง

เจ้าของโครงการเป็นผู้อนุมัติการเลื่อนความรู้เข้าสู่สถานะ `validated` และ `canonical` รวมถึงการเปลี่ยนแปลงสำคัญใน skills

## เป้าหมาย

1. เชื่อมความรู้ที่เจ้าของโครงการเรียนรู้กับความสามารถและวิธีทำงานของ Agent
2. รวมความรู้จากเจ้าของโครงการและ Agent ไว้ใน repository เดียวที่ค้นหา อ้างอิง และตรวจประวัติได้
3. ให้ Agent อื่นดึงความรู้ที่ผ่านการตรวจสอบไปใช้ และเสนอความรู้กลับเข้าสู่กระบวนการตรวจรับได้
4. แยกความรู้ วิธีคิด ความสามารถที่ต้องการ ขั้นตอนสำหรับ Agent และผลประเมินออกจากกัน
5. ประเมินว่า skills และวิธีการช่วย Agent ทำงานได้ตามที่ตั้งใจ โดยเก็บหลักฐานและผลการทดลอง

## ขอบเขตระยะแรก

- ใช้ Git และ Markdown เป็นแกนของคลัง โดย Git history เก็บประวัติการเปลี่ยนแปลง
- ให้ Agent จาก repository อื่นเข้าถึงแหล่งกลางผ่าน Git remote เมื่อมีการตั้งค่า remote และสิทธิ์แล้ว
- เริ่มค้นจากดัชนี จากนั้นอ่านเฉพาะเนื้อหาที่เกี่ยวข้อง
- ใช้ Pull Request (PR) เป็นช่องทางตรวจทานและอนุมัติการเปลี่ยนแปลงบน remote ที่รองรับ PR
- จัด skills เป็นแพ็กเกจตามรูปแบบเปิด Agent Skills โดยใช้ `SKILL.md` และไฟล์อ้างอิงที่จำเป็น
- เริ่ม evaluation จากบันทึกและตัวอย่างงานใน repository ก่อนเพิ่มเครื่องมือเฉพาะ

### สิ่งที่ยังไม่ใช่เป้าหมายระยะแรก

- สร้างเว็บแอป ฐานข้อมูล ระบบค้นหาเชิงความหมาย (RAG) หรือ MCP server เฉพาะ
- ซิงก์ความรู้ให้ทุก Agent โดยอัตโนมัติ หรือให้ระบบเลื่อนความรู้เป็น `canonical` โดยไม่ผ่านเจ้าของ
- กำหนดว่าทุก Agent จะค้นพบหรือประยุกต์ใช้ skill แบบเดียวกัน เครื่องมือปลายทางต้องรองรับรูปแบบนั้น
- เพิ่มระบบ evaluation หรือ CI ที่ซับซ้อนก่อนมีกรณีใช้งานซ้ำซึ่งต้องวัดผล

## โครงสร้างความรู้และขอบเขต

| ตำแหน่ง | ใช้เก็บ |
|---|---|
| `knowledge/inbox/` | ความรู้หรือข้อเสนอที่ยังไม่ผ่านการตรวจสอบ ไม่ใช่คำแนะนำปฏิบัติงานโดยค่าเริ่มต้น |
| `knowledge/validated/` | ความรู้ที่ผ่านการตรวจสอบแล้ว แต่ยังไม่จำเป็นต้องเป็นมาตรฐานกลาง |
| `knowledge/canonical/` | ความรู้ที่ได้รับการยอมรับให้เป็นแหล่งอ้างอิงหลัก |
| `methodologies/` | วิธีคิดและกระบวนการ |
| `capabilities/` | ความสามารถที่ต้องการให้ Agent ทำได้ |
| `skills/` | Implementation สำหรับ Agent ในรูปแบบที่พกพาได้เมื่อ Agent ปลายทางรองรับ |
| `experiments/` | สมมติฐาน วิธีทดลอง ผลที่สังเกตได้ เกณฑ์ประเมิน และ Evaluation |
| `decisions/` | Architecture Decision Records (ADR) |

ความรู้ควรแยกเป็นไฟล์ตามหัวข้อ และเชื่อมกันด้วยดัชนีกับลิงก์อ้างอิง ความรู้แต่ละรายการควรระบุแหล่งที่มา ขอบเขตการใช้ และสถานะ เมื่อเลิกใช้ให้เก็บประวัติพร้อมชี้ไปยังรายการที่มาแทน

## วงจรการเรียนรู้และการใช้งาน

1. เจ้าของโครงการหรือ Agent บันทึกความรู้ใหม่หรือข้อเสนอไว้ใน `knowledge/inbox/` หรือบันทึกการทดลองไว้ใน `experiments/`
2. ข้อเสนอต้องมีบริบทและหลักฐานเพียงพอให้ตรวจสอบได้ Agent เสนอได้ แต่ไม่เปลี่ยนความรู้ที่รับรองแล้วโดยตรง
3. เจ้าของโครงการตรวจสอบและตัดสินว่าจะยอมรับ แก้ไข ปฏิเสธ หรือเลื่อนรายการไป `validated/` หรือ `canonical/`
4. เมื่อความรู้ชัดเจนพอและต้องการให้ Agent ทำซ้ำได้ จึงพัฒนาเป็น capability หรือ skill พร้อมลิงก์ไปยังความรู้ที่รองรับ
5. ทดสอบ skill หรือวิธีการกับงานตัวอย่าง บันทึกเกณฑ์และผลใน `experiments/` แล้วใช้ผลประกอบการปรับปรุง
6. เมื่อ Agent จากโปรเจกต์อื่นทำงาน ให้ดึง repository ล่าสุด อ่านดัชนี เลือกใช้ `canonical` ที่เกี่ยวข้อง และเสนอการเรียนรู้กลับเข้าสู่ขั้นตอนตรวจรับ

Agent อาจใช้ `validated` เมื่อจำเป็นโดยต้องคงสถานะความไม่เป็นมาตรฐานให้ชัดเจน หากคำแนะนำขัดกับโจทย์หรือบริบท Agent ต้องชี้แจงแหล่งที่ขัดกันและถามเจ้าของโครงการก่อนตัดสินใจเรื่องสำคัญ

## แนวทางเครื่องมือและทางเลือก

แนวทางหลักคือ **Git + Markdown + PR review + Agent Skills** เพราะใช้รูปแบบไฟล์ที่ตรวจสอบและย้ายออกได้ง่าย แบ่งความรับผิดชอบได้ชัด และมีภาระเริ่มต้นต่ำ Git/GitHub ไม่ได้บังคับความหมายของสถานะ HACLS เอง จึงต้องมีดัชนี คู่มือ และ checklist สำหรับการตรวจรับ

พิจารณาเพิ่ม **MkDocs** เมื่อการค้นหรือ browse ในไฟล์เริ่มติดขัด และเพิ่มเครื่องมือ evaluation เช่น Promptfoo หรือ Inspect AI เมื่อมี skills หรืองานที่ต้องเปรียบเทียบผลซ้ำอย่างจริงจัง MCP server หรือเว็บแอปเป็นทางเลือกภายหลัง หาก Agent ไม่สามารถเข้าถึง Git ได้สะดวกหรือเกิดข้อจำกัดที่พิสูจน์ได้

การประเมินภาระบำรุงรักษา: ต่ำในระยะแรก และปานกลางเมื่อเพิ่มเว็บไซต์ การตรวจลิงก์/metadata และ evaluation CI; สูงเมื่อสร้างระบบเฉพาะที่ต้องดูแลโค้ด การโฮสต์ การยืนยันตัวตน สิทธิ์ การซิงก์ และการติดตามระบบ การประเมินนี้เป็นข้อสรุปเชิงออกแบบ ไม่ใช่ benchmark เชิงปริมาณ

## หลักการดูแลและความปลอดภัย

- ใช้ภาษาไทยเป็นหลัก ชื่อไฟล์และฟิลด์มาตรฐานใช้ภาษาอังกฤษเมื่อรูปแบบกำหนด
- ใช้สิทธิ์อ่านแยกจากสิทธิ์เขียน; การเข้าถึงคลังไม่ได้แปลว่า Agent มีสิทธิ์เปลี่ยนแหล่งอ้างอิงหลัก
- ห้ามเก็บ secrets, credentials และข้อมูลส่วนบุคคลที่ไม่จำเป็นใน repository
- เครื่องมือตรวจ secret เป็นเพียงแนวป้องกันเสริม ยังต้องตรวจเนื้อหาที่อาจเป็นข้อมูลอ่อนไหวด้วยคน
- Agent Skills เป็นรูปแบบแพ็กเกจ ไม่รับประกันว่า Agent ทุกผลิตภัณฑ์จะค้นพบ โหลด หรือปฏิบัติตาม skill เหมือนกัน ต้องตรวจสอบกับ Agent ที่ใช้จริง

## เกณฑ์ความสำเร็จ

- ความรู้ใหม่ที่เจ้าของโครงการเรียนรู้สามารถเชื่อมไปสู่ capability หรือ skill ที่ Agent นำไปใช้กับงานได้
- Agent สามารถเสนอสิ่งที่เรียนรู้พร้อมหลักฐาน และความรู้นั้นถูกตรวจสอบ จัดสถานะ และนำกลับมาใช้ได้
- Agent จากโปรเจกต์อื่นค้นพบและอ้างอิงความรู้ที่เกี่ยวข้องจาก repository นี้ได้
- skills ที่ได้รับการยอมรับมีความรู้ต้นทางและผลการทดลองรองรับ

ระยะแรกใช้หลักฐานจากงานจริงและการทบทวนของเจ้าของโครงการ ยังไม่กำหนดเป้าหมายตัวเลขจนกว่าจะมีข้อมูลการใช้งาน

## เงื่อนไขเริ่มใช้งานข้ามโปรเจกต์

workspace ปัจจุบันเป็น Git repository บน branch `dev` และมี remote ชื่อ `origin` แล้ว ก่อนใช้งานข้ามโปรเจกต์ยังต้องตรวจว่า Agent ปลายทางมีสิทธิ์อ่านและ clone/pull ได้ และกำหนดสิทธิ์เขียนแยกตามบทบาท
