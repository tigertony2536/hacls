# Architecture Pattern Toolkit: ภาพรวม

> **สถานะความรู้:** Inbox — ข้อเสนอเริ่มต้น รอตรวจสอบกับแหล่งอ้างอิงและบริบทจริง
> **อัปเดตล่าสุด:** 2026-10-30

## สรุป

คลังนี้รวบรวม design pattern และ architecture ที่อาจช่วยแก้ปัญหาซ้ำ ๆ ในระบบ พร้อมบันทึก trade-off เงื่อนไขการใช้ และคำถามเพื่อช่วยเลือกอย่างมีเหตุผล เป้าหมายคือช่วยให้เปรียบเทียบทางเลือกจากปัญหาและข้อจำกัดของระบบ ไม่ใช่สะสมชื่อ pattern หรือใช้รูปแบบเดียวกับทุกระบบ

## ขอบเขต

- **ครอบคลุม:** pattern ระดับ application, data, integration และ operations; ปัญหาที่ pattern ตั้งใจแก้; เงื่อนไขก่อนใช้; ต้นทุนและทางเลือกอื่น
- **ไม่ครอบคลุม:** การรับรองว่ารูปแบบหนึ่งเหมาะกับระบบ HACLS โดยอัตโนมัติ หรือการแทนที่การวิเคราะห์ข้อกำหนดและ failure mode ของระบบจริง

## วิธีใช้คลัง

สำหรับแต่ละ pattern ให้บันทึกอย่างน้อย: ปัญหาที่พบ, กลไกการทำงาน, บริบทที่เหมาะ/ไม่เหมาะ, trade-offs, failure modes, ทางเลือกที่ง่ายกว่า, สัญญาณว่าควรนำมาใช้ และแหล่งอ้างอิง

เริ่มจากคำถามว่า “ระบบกำลังมีปัญหาอะไร และต้องการคุณสมบัติใด” แล้วค่อยเปรียบเทียบ pattern ที่เกี่ยวข้อง การมี pattern อยู่ใน catalog ไม่ใช่เหตุผลเพียงพอที่จะเพิ่มมันเข้า architecture

- “JCM3” หมายถึงระบบ/เอกสารใด และมี URL หรือชื่อบทความที่ควรอ้างอิงหรือไม่?
- ควรใช้โครงสร้าง profile เดียวกันกับทุก pattern หรือแยกตามระดับ (code, application, distributed system)?
- จะเพิ่มเกณฑ์คัดเลือกที่เชื่อมกับคุณสมบัติคุณภาพ เช่น reliability, operability, latency และต้นทุนอย่างไร?
