# Pattern Catalog: เริ่มจากปัญหา แล้วค่อยเลือกเครื่องมือ

รายการนี้เป็นแผนที่หัวข้อสำหรับศึกษา ไม่ใช่รายการ pattern ที่ผ่านการรับรองหรือข้อบังคับทางสถาปัตยกรรม ก่อนเพิ่ม pattern ให้ระบุปัญหาและคุณสมบัติที่ต้องการก่อน

| ปัญหาหรือแรงกดดัน | Pattern ที่ควรศึกษา | คำถามคัดเลือกเบื้องต้น |
|---|---|---|
| งานประมวลผลบางรายการล้มเหลวและต้องตรวจสอบ/ลองใหม่ | Quarantine Table, Dead Letter Queue, Retry with Backoff | ต้องเก็บ payload และบริบทการล้มเหลวนานเท่าใด? การลองซ้ำปลอดภัยหรือไม่? |
| ต้องประสานการเปลี่ยนข้อมูลกับการส่ง event | Transactional Outbox, Inbox/Idempotent Consumer | ต้องการ atomicity ระหว่าง database กับ broker แค่ไหน? |
| ขั้นตอนธุรกิจยาวและมีหลายบริการ | Saga, Process Manager | มีการชดเชยเมื่อบางขั้นล้มเหลวได้หรือไม่? ใครเป็นเจ้าของ workflow? |
| ต้องแยกการอ่านและเขียนเพื่อรองรับโหลดหรือรูปแบบข้อมูลต่างกัน | CQRS, Read Model/Projection | ความซับซ้อนและ eventual consistency คุ้มกับประโยชน์หรือไม่? |
| ต้องจำลอง/แยกการพึ่งพาระบบภายนอก | Anti-Corruption Layer, Adapter | ขอบเขตการแปลงข้อมูลและเจ้าของสัญญาอยู่ตรงไหน? |
| ต้องควบคุมความล้มเหลวระหว่างบริการ | Timeout, Circuit Breaker, Bulkhead | มี timeout และขีดจำกัด concurrency ที่เหมาะสมแล้วหรือยัง? |

## เกณฑ์เปรียบเทียบ

เมื่อเขียน profile ของ pattern ให้ตอบคำถามเหล่านี้:

1. ปัญหาและ failure mode ที่ pattern แก้คืออะไร?
2. กลไกหลักและ invariants ที่ต้องรักษามีอะไรบ้าง?
3. ต้องมี dependency, storage, worker หรือ operational process เพิ่มอะไร?
4. มี trade-off ด้านความซับซ้อน, latency, consistency, ต้นทุน และการดูแลอย่างไร?
5. เมื่อใดควรเลือกทางเลือกที่ง่ายกว่า หรือไม่ใช้ pattern นี้?
6. จะสังเกตและกู้คืนเมื่อ pattern ทำงานผิดพลาดอย่างไร?

## การเลือกเบื้องต้น

- เริ่มจาก failure mode หรือข้อจำกัดที่เกิดขึ้นจริง ไม่เริ่มจากชื่อ pattern
- เปรียบเทียบอย่างน้อยหนึ่งทางเลือกที่ง่ายกว่า
- พิจารณาความสามารถของทีมในการปฏิบัติการและแก้ปัญหา ไม่ใช่เฉพาะโครงสร้างโค้ด
- บันทึกสมมติฐานและหลักฐานที่ใช้ตัดสินใจ
