# เครื่องมือจัดโครงสร้างการคิดสำหรับ Skills

เครื่องมือจัดโครงสร้างการคิดช่วยให้ skill ถามคำถาม วิเคราะห์หลักฐาน และเลือกขั้นตอนถัดไปได้เป็นระบบ เหมาะกับงานที่มีทางเลือกหลายทาง เงื่อนไข หรือ dependency ระหว่างการตัดสินใจ เครื่องมือแต่ละชนิดแก้ปัญหาคนละแบบ จึงควรเลือกตามลักษณะงาน และไม่จำเป็นต้องใช้ทุกแบบใน skill เดียว

## เครื่องมือและการใช้งาน

| เครื่องมือ | ใช้เมื่อ | ตัวอย่าง skill |
|---|---|---|
| **Decision tree** | คำตอบหนึ่งกำหนดคำถามหรือทางเลือกถัดไป | สัมภาษณ์เก็บ requirement, ช่วยตัดสินใจ |
| **State machine** | งานเดินผ่านสถานะที่มีกฎการเปลี่ยนขั้นชัดเจน | onboarding, incident response, approval workflow |
| **Decision table** | ต้องพิจารณาเงื่อนไขหลายข้อเพื่อเลือกผลลัพธ์ | triage, policy check, compatibility assessment |
| **Dependency graph** | งานหรือคำถามหลายส่วนต้องทำตามลำดับก่อนหลัง | วางแผน implementation, วิเคราะห์ dependency |
| **Checklist / rubric** | ต้องตรวจความครบถ้วนหรือประเมินตามเกณฑ์เดียวกัน | code review, readiness assessment |
| **Hypothesis tree** | มีสาเหตุที่เป็นไปได้หลายแบบและต้องหา evidence แยกแต่ละแบบ | debugging, root-cause analysis |
| **Bayesian update** | ต้องปรับระดับความเชื่อเมื่อมีหลักฐานใหม่และความไม่แน่นอนยังสูง | diagnosis, ประเมินสมมติฐานจากข้อมูลทยอยเข้ามา |
| **Impact–effort matrix** | ต้องจัดลำดับงานหรือตัวเลือกตามผลกระทบและต้นทุน | prioritization, backlog refinement |
| **Risk matrix / FMEA** | ต้องระบุและจัดลำดับความเสี่ยงก่อนลงมือหรือปล่อยระบบ | threat/risk assessment, release readiness |
| **Plan–execute–verify loop** | ต้องลงมือ ตรวจผล แล้วปรับแผนตามสิ่งที่เกิดขึ้น | แก้บั๊ก, migration, deploy |

## วิธีเลือกใช้

- ถ้าคำตอบกำหนดคำถามถัดไป ให้ใช้ **decision tree**
- ถ้าขั้นตอนเปลี่ยนตามสถานะของงาน ให้ใช้ **state machine**
- ถ้ามีกฎหลายข้อที่จับคู่กับผลลัพธ์ ใช้ **decision table**
- ถ้าต้องจัดลำดับงานตาม prerequisite ใช้ **dependency graph**
- ถ้าต้องตรวจซ้ำอย่างสม่ำเสมอ ใช้ **checklist / rubric**
- ถ้ากำลังค้นหาสาเหตุ ให้ใช้ **hypothesis tree** และปรับสมมติฐานตามหลักฐาน
- ถ้าต้องทำงานเชิงปฏิบัติการหลายรอบ ให้ใช้ **plan–execute–verify loop**

เครื่องมือเหล่านี้ผสมกันได้เมื่อหน้าที่ต่างกัน เช่น skill สำหรับ debugging อาจใช้ hypothesis tree เพื่อเลือกสาเหตุที่จะตรวจ แล้วใช้ plan–execute–verify loop เพื่อทดสอบ ส่วน skill สำหรับ requirements อาจใช้ decision tree ในการสัมภาษณ์ และ dependency graph ในการจัดลำดับงานที่ได้มา

## หลักการออกแบบ

1. เลือกเครื่องมือที่ตรงกับรูปแบบปัญหา แทนการเพิ่มโครงสร้างโดยไม่จำเป็น
2. ระบุข้อมูลนำเข้า เงื่อนไขในการไปต่อ และผลลัพธ์ที่ skill ต้องสร้างให้ชัด
3. แยกข้อเท็จจริงที่ agent ควรค้นเอง ออกจากการตัดสินใจที่ต้องถามผู้ใช้
4. เมื่อมีการถามเป็นรอบ ให้ถามเฉพาะคำถามที่ prerequisite พร้อมแล้ว และอัปเดตโครงสร้างตามคำตอบ
5. จบเมื่อไม่มีคำถามหรือการตรวจสอบที่จำเป็นค้างอยู่ และมีผลลัพธ์ที่ผู้ใช้ตรวจทานได้

## ความเกี่ยวข้อง

- เชื่อมโยงกับการออกแบบ workflow สำหรับ Agent Skills
- Decision tree เป็นแนวคิดที่ใช้กับการสัมภาษณ์แบบเป็นรอบ เช่น skill `grilling` ของ Matt Pocock
